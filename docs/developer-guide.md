# Руководство разработчика

## 1. Архитектура

Путь данных в приложении:

```text
React UI (src/)
  -> Tauri invoke (src/storage.js)
  -> Tauri-команды и DTO (app/src/main.rs)
  -> planner-storage (src-tauri/src/lib.rs)
  -> SQLite (база в app-data)
```

React отвечает за интерфейс и оперативное состояние. `src/storage.js` задаёт типизированные вызовы команд Tauri. `app/src/main.rs` является адаптером транспортных DTO и держит соединение SQLite в состоянии приложения. Библиотека `planner-storage` содержит операции хранения, транзакции, поиск/статистику и резервное копирование. Схема создаётся последовательными миграциями.

Файл базы называется `planner.sqlite` и размещается в каталоге `app_data_dir` Tauri (на Windows обычно `%APPDATA%\com.planner.app\planner.sqlite`). Инициализация/ошибка миграции не должна подменяться созданием пустой базы.

Более подробные схемы потоков, модулей и таблиц см. в [архитектуре](../SA/architecture.md).

## 3. Требования к среде

Подтверждённая среда разработки/сборки — Windows x64:

- Node.js 20.19+ (или 22.13+ / 24+; проект проверялся на Node.js 22);
- Rust stable;
- MSVC Build Tools для нативных зависимостей;
- WebView2 Runtime для запуска приложения;
- Tauri CLI 2 для `cargo tauri dev` и сборки установщика.

SQLite подключается через `rusqlite` с bundled SQLite.

## 4. Сборка и запуск

Из корня проекта в PowerShell:

```powershell
npm ci
npm test
cargo test --manifest-path .\src-tauri\Cargo.toml
cargo check --manifest-path .\app\Cargo.toml
```

Запуск десктопного приложения:

```powershell
Set-Location .\app
cargo tauri dev
```

Сборка установщика:

```powershell
Set-Location .\app
cargo tauri build
```

Tauri запускает `npm run build` перед dev/build. Frontend собирается esbuild в `app/frontend/bundle.js`; это генерируемый файл, его не следует редактировать вручную. Результаты релизной сборки находятся в `app/target/release/`, установщики — в `app/target/release/bundle/`.

`npm test` сначала собирает frontend, затем запускает тесты сценариев интервалов, диапазонов шаблонов, повторов, локализации, PlanScript, mock-backend и перемещения событий.

При запуске календарь ждёт только настройки, категории и данные текущей недели; шаблоны, задачи, события на весь день и календарные метаданные загружаются после первого отображения. В обычном режиме DOM создаётся для текущей недели, а другие недели монтируются по мере приближения к ним при прокрутке. Пустое зарезервированное место заменяется скелетоном с вращающейся иконкой, когда неделя входит в буфер прокрутки; тяжёлая сетка монтируется с небольшой задержкой и только после получения данных.

Пока загружаются обязательные данные стартового экрана, показывается скелетон недельной сетки с анимированной иконкой приложения; анимация отключается при `prefers-reduced-motion`. Стартовый и прокручиваемый скелетоны, а также отложенное монтирование недели проверяются в mock-backend smoke-тесте. В недельной сетке поиск интервала по времени использует двоичный поиск по отсортированным интервалам, а категории индексируются по ID на рендер недели.

## 5. Изменение схемы и модели данных

### Добавление миграции

1. Создайте следующий нумерованный SQL-файл в `src-tauri/migrations/`.
2. Подключите его через `include_str!` и добавьте последовательную обработку версии в `init_schema_if_needed` в `src-tauri/src/lib.rs`.
3. Убедитесь, что существующая база обновляется без потери данных, а чистая база получает итоговую схему.
4. Добавьте интеграционные тесты миграции и операций, включая откат при ошибке для пакетных записей.
5. Проверьте запуск полного набора Rust-тестов и `cargo check` приложения.

Текущая схема доходит до версии 8. Не редактируйте ранее выпущенную миграцию ради изменения схемы: добавляйте следующую версию и предусмотрите переход со старых версий.

### Семантика интервалов

- `intervals` хранит непустые непрерывные интервалы по дате; время хранится в минутах от полуночи.
- Границы интервала кратны 5 минутам, конец строго больше начала и трактуется как исключительная граница.
- Свободное время отдельными строками не хранится.
- Интервалы в UI могут быть разрезаны или объединены при применении операции; сохраняйте семантику `[start, end)` и используйте существующие операции разрезания/объединения.
- События на весь день, задачи без времени, рефлексии и события сетки — разные сущности и отдельные таблицы.
- Шаблоны и правила повторов не владеют созданными интервалами как внешние ключи: календарные копии живут независимо.
- Пакетное применение шаблона/повтора должно оставаться транзакционным и атомарным.
- Очистка интервалов по диапазону строит снимки затронутых недель и использует `restore_weeks` одной транзакцией; Undo восстанавливает те же снимки. Не включайте в эту операцию события на весь день и задачи без времени.

ER-диаграмма и список полей таблиц приведены в [архитектуре](../SA/architecture.md); полный источник истины для DDL — файлы миграций.

## 6. Добавление backend-команды

При добавлении функции хранения согласованно обновите:

1. реализацию и типы/DTO в `src-tauri/src/lib.rs`;
2. Tauri-адаптер в `app/src/main.rs` и список `generate_handler!`;
3. клиентскую обёртку в `src/storage.js`;
4. компонент/поток UI и отображение ошибок;
5. тест storage и/или frontend.

Вызовы storage асинхронны. Обрабатывайте отказ `invoke` явно: ошибка записи не должна отображаться как успешное действие. Для больших групп изменений используйте backend-транзакцию, а не цикл независимых операций из UI.

При передаче объектов через Tauri используйте согласованный camelCase DTO и serde mapping. Для patch-полей, где нужно различать «не менять» и «сбросить в пустое значение», ориентируйтесь на существующий `Option<Option<T>>` в адаптере интервалов.

## 7. PlanScript

Текущая реализация разделена на:

- `src/script/lexer.js` — токены, отступы и позиции ошибок;
- `src/script/parser.js` — AST и синтаксис;
- `src/script/interpreter.js` — runtime, симуляция операций, read-only режим, наблюдатели и лимиты.

Тесты языка находятся в `tests-frontend/planscript.test.mjs`. [Спецификация](../SA/planscript-spec.md) включает проектируемые возможности; она не заменяет тесты и исходный код как описание доступного поведения. При расширении обновляйте тесты и документацию, не добавляя исполнение произвольного JavaScript или прямой SQL-доступ из сценария.

В текущем runtime заданы пределы до 200 000 операций, 1 000 000 шагов, 60 дат-зависимостей для наблюдателя и не более трёх новых лет за один запуск. Не ослабляйте их без оценки производительности и безопасности.

## 8. Тестирование

Выбирайте минимальный набор, закрывающий изменение:

| Что изменено | Проверка |
|---|---|
| Логика интервалов на frontend | `node tests-frontend/intervals.test.mjs` |
| Выбор диапазонов шаблона | `node tests-frontend/template-range.test.mjs` |
| Генерация/конфликты повторов | `node tests-frontend/recurring-scenarios.test.mjs` и backend bulk tests |
| Переводы | `node tests-frontend/i18n.test.mjs` |
| Синтаксис/runtime PlanScript | `node tests-frontend/planscript.test.mjs` |
| Интеграция React со storage | `node tests-frontend/mock-backend-smoke-test.mjs` |
| Сценарий переноса | `node tests-frontend/move-scenario-test.mjs` |
| SQLite, транзакции, миграции | `cargo test --manifest-path .\src-tauri\Cargo.toml` |
| Итоговая проверка frontend | `npm test` |

При изменении формы данных проверьте оба направления: отображение сразу после операции и восстановление данных из SQLite после повторной загрузки/перезапуска.

## 9. Ошибки и диагностика

- Ошибка запуска может возникнуть при недоступном app-data каталоге, проблеме схемы/миграции или невозможности открыть SQLite. Не заменяйте её молчаливым стартом на пустой базе.
- Для UI проверяйте консоль WebView/DevTools; при неудаче `invoke` выводите сообщение пользователю и сохраняйте техническую ошибку в журнале разработки.
- Если после изменения frontend появляется пустое окно, остановите `cargo tauri dev` и запустите снова: Tauri пересобирает bundle перед стартом.
- Уведомления требуют разрешения ОС и доступны, пока приложение запущено.
- Перед диагностикой импорта/восстановления сохраните отдельную копию базы JSON.

## 10. Упаковка и область поддержки

Конфигурация Tauri задаёт установщики MSI и NSIS, имя продукта «Незабудка» и идентификатор `com.planner.app`. Для Windows-сборки нужны рабочие MSVC-инструменты и WebView2. Другие ОС не считаются поддержанными до отдельной сборки, тестирования и документации процесса установки.

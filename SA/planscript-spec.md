# PlanScript — техническая спецификация

Версия: 1.1
Статус: утверждённая проектная спецификация для реализации и дальнейшей поддержки
Приложение: десктопный недельный планировщик FMN (React + Tauri + SQLite)

> Важно: спецификация фиксирует целевой контракт языка и может описывать функции, которые ещё не реализованы в текущем runtime. Фактическое поведение определяется `src/script/lexer.js`, `src/script/parser.js`, `src/script/interpreter.js` и `tests-frontend/planscript.test.mjs`. Для руководства по доступным пользовательским возможностям см. [руководство пользователя](../docs/user-guide.md).

## 1. Обзор

PlanScript — это доменный язык сценариев для массового заполнения и корректировки недельной сетки календаря. Он предназначен для случаев, когда стандартные панели шаблонов и повторов недостаточны: при необходимости применять сложные правила по чётным/нечётным неделям, диапазонам дат, условиям по уже существующим ячейкам, выборкам по категориям, динамическим расписаниям и другим сценариям, которые неудобно выражать в форме с чекбоксами.

Язык не является «мини-Python» и не пытается покрыть все задачи программирования. Его задача — дать человеку компактный, читаемый и безопасный способ описывать логические правила заполнения календаря, при этом обеспечивая:

- предсказуемость: один и тот же сценарий должен давать одинаковый результат при повторном запуске;
- безопасность: запрещены скрытые побочные эффекты и небезопасные операции записи;
- прозрачность: каждое действие может быть протестировано и просмотрено до применения;
- детерминизм: при конфликте перекрывающихся правил победителем является правило, которое выполнено позже в тексте сценария;
- локальную модель данных: сценарий работает с тем же доменом, что и календарь, а не вводит отдельную параллельную структуру.

## 2. Цели и принципы дизайна

### 2.1 Основной принцип

PlanScript строится вокруг двух уровней:

1. императивный каркас управления — циклы `for`, условия `if`, функции `def`, локальные переменные;
2. декларативные операции над календарём — методы и функции вроде `.category(...)`, `.text(...)`, `.set(...)`, `template(...).apply_to(...)`, `recur(...)`.

Такой подход делает сценарии читаемыми для человека и близкими к бизнес-логике: «по чётным неделям в среду с 9:00 до 11:00 выставить категорию “Учёба”».

### 2.2 Принципы

- Явное лучше неявного: некорректные интервалы, неподдерживаемые диапазоны, неподходящие типы и несуществующие категории — это ошибка, а не тихое округление или преобразование.
- Нет `while`: язык ориентирован на конечный домен данных — календарь и заранее известный диапазон дат. Любой сценарий можно выразить через конечный обход диапазона.
- Одна команда = один безопасный атомарный эффект: сценарий выполняется как единый транзакционный набор операций; пользователь получает одну отмену в истории.
- Нет скрытых «накопительных» записей: повторный запуск одного и того же сценария должен давать тот же результат, а не добавлять новые события поверх старых.
- Опасные операции должны быть явно помечены: сценарии имеют режим предпросмотра и проверки перед применением; отсутствие подтверждения = безусловный запрет на запись.
- Поддержка кириллицы в идентификаторах: логика и имена пользовательских сущностей могут быть на русском языке, тогда как ключевые слова языка — на английском.

## 3. Границы ответственности

PlanScript не заменяет:

- пользовательский интерфейс календаря;
- SQL-слой и модель хранения;
- панель повторяющихся событий и шаблоны как отдельные готовые пользовательские инструменты;
- полноценный язык общего назначения.

PlanScript дополняет их, предоставляя выразительный и безопасный сценарный слой для автоматизации сложных правил.

## 4. Контекст исполнения и интеграция с приложением

### 4.1 Архитектурная роль

В текущей архитектуре FMN PlanScript является частью клиентского слоя `src/script/`:

- `src/script/lexer.js` — лексер;
- `src/script/parser.js` — синтаксический анализатор;
- `src/script/interpreter.js` — интерпретатор и runtime.

Он работает поверх данных и объектов календаря, описанных в [архитектуре FMN](./architecture.md) и уровне хранения Tauri/SQLite.

### 4.2 Модель данных

PlanScript не вводит отдельную наборную модель. Он оперирует теми же сущностями, которые существуют в проекте:

- `Category` и `Subcategory`;
- `Day`, `Week` и `Selection`;
- `intervals` как непрерывные временные интервалы на день;
- `all_day_events` для событий, занимающих несколько дней;
- `todos` для задач без времени;
- `settings` для глобальных настроек недели/дня.

Результат выполнения сценария транслируется в операции низкого уровня, например:

- `SetInterval(date, startMin, endMin, patch)`;
- `ClearInterval(date, startMin, endMin)`;
- `SetAllDay(startDate, endDate, text, category, color)`;
- `ClearAllDay(id)`;
- `AddTodo(text)`.

Это важно: PlanScript не является независимым источником истины. Он является удобным DSL поверх существующего календаря.

## 5. Типы и литералы

### 5.1 Поддерживаемые типы

| Тип | Пример | Описание |
|---|---|---|
| Number | `12`, `3.5`, `-1` | Число, без жёсткого разделения int/float на уровне синтаксиса |
| String | `'Аудит'`, `"Аудит"` | Строка, одинарные и двойные кавычки равнозначны |
| Boolean | `true`, `false` | Логическое значение |
| None | `none` | Пустое значение |
| Date | `12.09.2026` | Дата в формате `ДД.ММ.ГГГГ` |
| Time | `09:30` | Время в формате `ЧЧ:MM` |
| Duration | `30m`, `2h`, `1h30m` | Длительность, преобразуемая в минуты |
| Range | `9:00..10:30` | Диапазон значений |
| List | `[1, 2, 3]` | Список значений |
| Category | `category('Учёба')` | Сущность категории |
| Subcategory | `subcategory('Аудит')` | Сущность подкатегории |
| Day / Week / Selection | `week.mon`, `day.time(...)` | Объекты домена календаря |

### 5.2 Значения и приведение

- В языке нет неявного “truthiness”: выражения в `if`, `elif`, `and`, `or`, `not` должны быть булевыми.
- Проверка на пустоту должна выполняться явно: `if len(items) > 0`, `if text != none`.
- Значения и типы контролируются на этапе компиляции/проверки и во время исполнения.

### 5.3 Комментарии и интерполяция строк

- Комментарий начинается с `#` и действует до конца строки.
- Первая строка, начинающаяся с `# strict: off`, включает строгий режим отключения; это исключение описано далее.
- Внутри строк поддерживается интерполяция: `${expr}`.

Пример:

```plan
text = "Неделя ${week.index}: ${subject.name}"
```

## 6. Синтаксис языка

### 6.1 Базовые правила

- Отступы обязательны для блоков `for`, `if`, `def`, `watch`.
- Запрещены табы в отступах.
- Разделение операторов выполняется переводом строки.
- Скобки `()`, `[]`, `{}` могут быть вложенными.

### 6.2 Операторы

Поддерживаются:

- присваивание: `=`, `+=`, `-=`, `*=`, `/=`;
- сравнение: `==`, `!=`, `<`, `<=`, `>`, `>=`, `in`, `not in`;
- логические операции: `and`, `or`, `not`;
- арифметика: `+`, `-`, `*`, `/`, `%`;
- диапазон: `..`.

### 6.3 Ключевые слова

```text
for in if elif else and or not
true false none
def return break continue
assert watch every
mon tue wed thu fri sat sun
```

### 6.4 Структура программы

```ebnf
program        ::= { statement } ;
statement      ::= simple_stmt | compound_stmt ;
compound_stmt  ::= for_stmt | if_stmt | def_stmt | watch_stmt ;
for_stmt       ::= "for" NAME { "," NAME } "in" expr ":" block ;
if_stmt        ::= "if" expr ":" block { "elif" expr ":" block } [ "else" ":" block ] ;
def_stmt      ::= "def" NAME "(" [ params ] ")" ":" block ;
```

## 7. Объекты домена календаря

### 7.1 `Day`

Представляет один день календаря.

Основные свойства:

- `.date` — дата;
- `.weekday` — день недели;
- `.week` — ссылка на неделю;
- `.is_empty` — пуст ли день;
- `.is_weekend` — выходной ли день.

Основные методы:

- `.time(start..end)` — выбрать временной диапазон;
- `.free_slots(min_duration=none)` — вернуть свободные интервалы дня;
- `.all_day` — обработка событий на весь день;
- `.indicator` — индикатор наблюдателя (если используется watch).

### 7.2 `Week`

Представляет неделю.

Полезные свойства:

- `.start`, `.end` — границы недели;
- `.index` — индекс внутри текущего цикла;
- `.iso_number` — ISO-номер недели;
- `.order` — текстовый номер недели в плитке;
- `.mon` .. `.sun` — дни недели;
- `.days` — список дней.

### 7.3 `Selection`

Представляет выделенный диапазон внутри дня.

Пример:

```plan
day.time(9:00..10:30)
    .category('Учёба')
    .subcategory('Аудит')
    .text('Лекция 307В')
```

Selection — основной объект мутации: у него есть методы `category`, `subcategory`, `color`, `text`, `task`, `done`, `clear`, `set`, `move_to`, а также свойства `.day`, `.start`, `.end`.

### 7.4 `Category` и `Subcategory`

Категории и подкатегории являются первичными сущностями домена календаря. Подкатегория всегда принадлежит конкретной категории.

Примеры:

```plan
эб = category('Учёба ЭБ', new=true)
аудит = эб.subcategory('Аудит', new=true)
```

Если категория или подкатегория не существует и `new=true` не передан, выполнение прекращается с понятной ошибкой.

## 8. Основные встроенные функции и API

### 8.1 Итерация по диапазонам

```plan
days(01.09.2026..09.09.2026)
weeks(01.09.2026, count=12)
weeks(today(), count=8)
```

- `days(...)` — возвращает последовательность дней;
- `weeks(...)` — возвращает последовательность недель;
- `range(a, b, step)` — возвращает последовательность чисел;
- `today()` / `now()` — дата и время текущего момента.

### 8.2 Получение категорий и шаблонов

```plan
category('Работа')
category('Работа', new=true)
subcategory('Налоги')

template('Учебная неделя').apply_to(weeks(...), mode=replace)
```

Поддерживаются режимы шаблона:

- `replace` — заменить всё;
- `fill_empty` — заполнить только пустые клетки;
- `overlay` — наложить поверх существующих данных.

### 8.3 Повторяющиеся правила

```plan
recur(
  weekday=mon,
  time=9:00..10:30,
  category='Учёба',
  weeks='1-4,7-9',
  pattern='all'
)
```

`recur(...)` — прямой сценарный аналог панели повторяющихся событий; он работает с теми же понятиями повторения, конфликтов и диапазона недель.

### 8.4 Поиск и статистика

```plan
find(day.time(17:00..19:00), text_contains='Спорт')
stats.hours('Учёба', weeks(01.09.2026, count=4))
```

- `find(...)` — поиск существующих интервалов по критериям;
- `stats.hours(...)` — суммарное количество часов по категории;
- `day.free_slots(...)` — поиск свободных “дырок” в расписании.

## 9. Управляющие конструкции

### 9.1 `for`

```plan
for week in weeks(01.09.2026, count=12):
    for day in week.days:
        if day.is_weekend:
            continue
        day.time(9:00..10:00).category('Работа')
```

Поддерживаются:

- обычный `for` по спискам и диапазонам;
- распаковка значений: `for i, week in enumerate(weeks(...))`;
- `break` и `continue` в теле цикла;
- `enumerate` и `zip`.

### 9.2 `if` / `elif` / `else`

```plan
if week.index % 2 == 0:
    ...
elif week.order == '12':
    ...
else:
    ...
```

В `if` допустимы только булевы выражения; `if text:` не допускается.

### 9.3 `def`

Функции поддерживают позиционные и именованные параметры, но без `*args`.

```plan
def лекция(куда, начало, конец, тема):
    куда.time(начало..конец).category('Учёба').text(тема)
```

Рекурсия допустима, но ограничена лимитом глубины и ресурсами исполнения.

### 9.4 `assert`

```plan
assert(len(items) > 0, 'Список пуст')
```

Если условие ложно, сценарий прекращается без частичного применения. Это сознательно не механизм восстановления исключений; язык не поддерживает `try/except` как часть DSL.

## 10. Безопасность и гарантия корректности

### 10.1 Нормальный режим: dry-run и preview

PlanScript работает по модели, при которой вычисления выполняются в два этапа:

1. разбор и проверка сценария;
2. построение списка операций и их симуляция на копии состояния;
3. просмотр diff до применения;
4. применение как единая транзакция.

Это гарантирует, что сценарий можно проверить до записи и увидеть, что именно изменится.

### 10.2 Идемпотентность

Сценарий должен быть идемпотентным: повторный запуск без изменения входных данных не должен давать дополнительный эффект.

Это достигается за счёт:

- явной перезаписи данных в целевых клетках;
- замены, а не накопления значений;
- атомарного применения пакета операций.

### 10.3 Конфликты и приоритеты

Если два действия в сценарии затрагивают один и тот же временной диапазон, побеждает более позднее действие по тексту сценария. Это соответствует модели ручной перекраски: последнее написанное правило имеет приоритет.

## 11. Ошибки и диагностика

### 11.1 Обязательная валидация

Ошибки должны возникать при:

- некорректном синтаксисе;
- неверном диапазоне или длительности;
- отсутствии категории/подкатегории;
- попытке записи в несуществующий день/неделю;
- конфликте режимов или типовых ограничений;
- попытке использовать “truthy”/“falsy” значения в условии.

### 11.2 Ограничения

Во время исполнения допустимы лимиты:

- максимум операций в одном сценарии;
- ограничение глубины рекурсии;
- ограничение на размер области чтения для наблюдателей;
- ограничение на количество новых лет, которые один запуск может создать в данных.

Такие лимиты — часть безопасности и предсказуемости.

## 12. Механизм наблюдателей (`watch`)

`watch` — реактивный блок, который вычисляет формулу на основе текущего состояния данных и обновляет один индикатор/результат.

Пример:

```plan
watch every day:
    if day.colored_hours > 16:
        day.indicator.set(color=#FF0000, text='Перегруз')
    else:
        day.indicator.clear()
```

### 12.1 Ограничения watch

- наблюдатель не должен иметь таймеров и фоновых циклов;
- он реагирует на изменения в зависимостях своих данных;
- он пишет только в свой собственный indicator;
- он не может читать результат другого наблюдателя, чтобы избежать циклических зависимостей.

## 13. Терминал и режим чтения

Отдельный терминальный режим предназначен для анализа уже существующих данных без записи.

Примеры:

```plan
len(find(day.time(17:00..19:00), text_contains='Спорт'))
count_cells(scope, category='Работа')
```

В терминале запрещены мутирующие операции: `.category()`, `.clear()`, `.set()`, `.append()`, `category(..., new=true)` и др. — выполнение завершается с понятной ошибкой.

## 14. Полная ориентировочная грамматика

```ebnf
program        ::= { statement } ;
statement      ::= simple_stmt NEWLINE | compound_stmt ;
simple_stmt    ::= assign_stmt | expr_stmt | return_stmt | break_stmt | continue_stmt | assert_stmt ;
compound_stmt  ::= for_stmt | if_stmt | def_stmt | watch_stmt ;
for_stmt       ::= "for" NAME { "," NAME } "in" expr ":" block ;
if_stmt        ::= "if" expr ":" block { "elif" expr ":" block } [ "else" ":" block ] ;
def_stmt       ::= "def" NAME "(" [ params ] ")" ":" block ;
watch_stmt     ::= "watch" "every" NAME ":" block ;
block          ::= NEWLINE INDENT statement { statement } DEDENT ;
assign_stmt    ::= NAME ("=" | "+=" | "-=" | "*=" | "/=") expr ;
assert_stmt    ::= "assert" "(" expr "," expr ")" ;
expr           ::= or_expr ;
or_expr        ::= and_expr { "or" and_expr } ;
and_expr       ::= not_expr { "and" not_expr } ;
not_expr       ::= "not" not_expr | comparison ;
comparison     ::= range_expr { cmp_op range_expr } ;
range_expr     ::= additive [ ".." additive ] ;
additive       ::= term { ("+" | "-") term } ;
term           ::= factor { ("*" | "/" | "%") factor } ;
factor         ::= [ "-" ] postfix ;
postfix        ::= primary { "." NAME | "(" [ args ] ")" | "[" expr "]" } ;
primary        ::= NUMBER | STRING | DATE_LIT | TIME_LIT | DURATION_LIT
                  | COLOR_LIT | "true" | "false" | "none" | NAME
                  | "(" expr ")" | list_lit ;
list_lit       ::= "[" [ expr { "," expr } ] "]" ;
```

## 15. Примеры сценариев

### 15.1 Базовое заполнение расписания

```plan
эб = category('Учёба', new=true)
математика = эб.subcategory('Математика', new=true)

for week in weeks(01.09.2026, count=12):
    for day in [week.mon, week.wed, week.fri]:
        day.time(09:00..10:30)
            .category(эб)
            .subcategory(математика)
            .text('Математика')
```

### 15.2 Чётные и нечётные недели

```plan
for week in weeks(01.09.2026, count=12):
    if week.index % 2 == 0:
        week.mon.time(12:00..14:00).category('Работа')
    else:
        week.mon.time(12:00..13:00).category('Самообразование')
```

### 15.3 Динамический список данных

```plan
расписание = [
    [mon, 08:30, 10:00, 'Аудит', '1-2,5-17'],
    [wed, 10:00, 11:30, 'ПОДФТ', '2-5,8-17'],
]

for week in weeks(01.09.2026, count=17):
    for запись in расписание:
        день, начало, конец, тема, недели = запись
        if weeks_match(week.index, недели):
            week.day(день).time(начало..конец).category('Учёба').text(тема)
```

## 16. Реализационные замечания

Текущий проект уже содержит базовую реализацию языкового стека в `src/script/`:

- лексер разбивает выражения и комментарии;
- парсер строит AST;
- интерпретатор исполняет сценарии и создает операции записи;
- runtime проверяет ограничения и переводит действия в модель календаря.

Следовательно, данная спецификация должна рассматриваться как контракт для дальнейшего расширения, а не как идеал, оторванный от кода. Любое изменение должен быть согласованно с:

- реальной синтаксической моделью `lexer.js` и `parser.js`;
- правилами `interpreter.js`;
- архитектурой FMN и схемой SQLite.

## 17. Рекомендации по дальнейшей разработке

1. Зафиксировать версию языка как канонический контракт для тестов.
2. Поддерживать единый набор встроенных функций и взаимодействие с `find`, `stats`, `recur`, `template`.
3. Сформировать набор unit-тестов на синтаксис и runtime-поведение.
4. Добавить строгую модель диагностики ошибок для пользовательских сценариев.
5. Сделать сухой прогон (dry-run) стандартным режимом выполнения в UI.

## 18. Заключение

PlanScript — это не универсальный язык программирования, а профилированный DSL для календарно-планировочных задач. Он решает основную проблему: сложные правила массового заполнения календаря должны быть выражены коротко, явно и безопасно.

Успех языка определяется не только возможностями синтаксиса, но и тем, насколько он сохраняет:

- предсказуемость;
- безопасный diff перед записью;
- читаемость для пользователя;
- прозрачность для разработчика и QA;
- согласованность с существующей моделью данных FMN.

Если он будет реализован в этом ключе, он станет важным инструментом для автоматизации планирования без потери контроля над данными.
